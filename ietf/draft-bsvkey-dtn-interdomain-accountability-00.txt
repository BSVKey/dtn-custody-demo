Accountability Between Administrative Domains in Delay-Tolerant Networks
             draft-bsvkey-dtn-interdomain-accountability-00

Abstract

   As bundles cross Administrative Domains run by different agencies and
   companies, each domain can show only its own logs of what it carried.
   This document describes how work already before the DTN Working Group
   fits together to give portable, independently verifiable evidence of
   inter-domain carriage: the DTN Peering Protocol for routes and domain
   identity, the Traceroute Extension Block for path diagnostics, signed
   custody receipts for evidence of holding, the Secure Bundle Audit
   Mechanism for dropped security operations, and the BPSec COSE
   context.  It proposes a small number of connections between them, all
   optional and none requiring a change to the Bundle Protocol:
   endorsing custodian keys with a domain's peering key, advertising a
   domain's receipt policy with its routes, checking a route's domain
   path against the custody evidence, an optional signature for
   traceroute hop-records, and sizing unsigned stretches with the Hop
   Count.

1.  Introduction

   The DTN Peering Protocol [I-D.taylor-dtn-dpp] describes the Solar
   System DTN as a set of Administrative Domains: space agencies,
   commercial operators and research networks that advertise
   reachability to one another.  Its own scenarios include a commercial
   operator advertising transit capacity to a government science
   network, and two agencies' networks exchanging traffic.

   Every one of those relationships raises the same questions after the
   fact.  Did the other domain carry the bundle?  When did it hold it?
   Which domains did a bundle actually cross, and did that match the
   route that was advertised?  Today the answers are each domain's own
   logs, which another domain can only take on trust.

   Several pieces of work before the DTN Working Group each address part
   of this.  This document does not define a new protocol.  It describes
   how those pieces fit, states the requirements they meet together, and
   proposes the connections that are missing.

   [I-D.koo-dtn-traceroute-eb].

3.  Requirements

   1.  Evidence is portable: a third party can verify it, later and
       offline, without contacting the domains that produced it.

   2.  Participation is optional per node and per domain; nodes that do
       not take part forward bundles as they do today.

   3.  No change to the Bundle Protocol or to BPSec is needed.

   4.  Missing evidence is reported as missing and never inferred.

   5.  Evidence is bound to a specific bundle and the payload bytes
       held, so it cannot be moved to another bundle.

   6.  Keys used for evidence chain to an identity the domains already

5.1.  Custodian Keys Endorsed by the Domain's Peering Key

   The custody receipt draft leaves key distribution out of scope.  DPP
   already gives every AD an Ed25519 key published in DNS at
   _dtn_domain.<AD-Domain> and verified by peers in a challenge-response
   handshake.  The same algorithm and the same key encoding (DER
   SubjectPublicKeyInfo, base64) are used by custody receipts.

   Proposal: an AD endorses each of its custodians with a small
   COSE_Sign1 by its DPP key over the custodian's node ID, public key
   and validity period.  A verifier that knows the AD (from the route,
   or from the custodian's node ID) fetches the AD key from DNS, checks
   the endorsement, and then checks the receipt.  Only one key per AD is
   published in DNS; custodian keys rotate without DNS changes.  How
   endorsements are distributed (with the bundle, over DPP, or by a
   published list) is an open question.

5.2.  Receipt Policy Advertised With Routes

   DPP advertisements carry extensible attributes.  Proposal: an
   optional attribute stating an AD's receipt policy for the routes it
   advertises: none, offered (its custodians sign when the block is
   present), or required (it will only carry bundles under a receipt
   agreement).  Peers can then prefer routes whose evidence they will be
   able to check.

5.3.  Checking a Route's Domain Path Against the Evidence

   A DPP route carries ad_path, the list of ADs it traverses.  Once a
   bundle is delivered, the ADs of its endorsed custodians can be
   compared with the ad_path of the route that was used.  A domain on
   the path with no receipt is a gap in the evidence; a receipt from a
   domain not on the path shows the bundle left the advertised route.
   Both are reported, neither is inferred.

5.4.  An Optional Signature for Traceroute Hop-Records

   The Traceroute Extension Block and the Custody Receipt Block record
   nearly the same facts per hop: the node, the node it received from,
   and a time.  TREB's records are, by its own security section,
   unauthenticated and diagnostic only.

   Proposal: an optional eighth element in a TREB hop-record, a
   COSE_Sign1 by the recording node with a detached payload (the CBOR
   encoding of the seven existing fields) and external additional
   authenticated data of the bundle identity and the SHA-256 of the
   payload block's data.  A reader that ignores the eighth element sees
   an unchanged TREB hop-record; a verifier with the node's key gets
   custody-grade evidence.  A shared hop-record shape lets diagnostics
   and accountability use one structure where both are wanted.

5.5.  Sizing Unsigned Stretches

   Both drafts observe that the Previous Node block names only the last
   node of an unsigned stretch.  TREB already uses the Hop Count block
   to count the hops made by transparent nodes.  Recording the Hop Count
   value in each custody receipt does the same for receipts, so a
   verifier can say how many unsigned hops lie between two signed ones.

5.6.  Per-Hop Block Lifecycle

   Blocks that nodes change in transit lose end-to-end BPSec protection
   by construction.  The receipt block and signed hop-records follow a
   third pattern: entries are appended, never changed, and each is
   signed by the node that added it, so earlier entries stay verifiable
   end to end without any BPSec operation outliving a hop.  Such blocks
   should not be targets of a BIB or BCB.  This is offered as input to
   the group's discussion of per-hop blocks.

5.7.  Settlement

   How domains price or settle carriage is out of scope.  This framework
   only ensures that bilateral agreements can refer to evidence both
   parties, and a third party, can check.  For high volumes, a custodian
   can sign one receipt per contact over a Merkle root of the bundles it
   held, with inclusion proofs per bundle, as the reference
   implementation does.

6.  Deployment

   Each connection is independent and optional.  Custody receipts are
   carried byte-identical today by µD3TN, NASA HDTN, JPL ION and Hardy,
   none of which implement them, and a payload BIB beside them still
   verifies.  A domain can start signing receipts without any peer
   changing, and verifiers report every stretch it does not cover.

7.  Open Questions

   *  Is the DTN Working Group the right home for inter-domain
      accountability, or only for its protocol pieces?

   *  How should custodian endorsements be distributed?

   *  Should the receipt policy attribute be defined in DPP or in a
      separate document?

   *  Would the TREB authors welcome an optional signed hop-record, and
      should custody receipts adopt the TREB hop-record shape?

8.  Security Considerations

   The framework rests on three assumptions: AD keys published in DNS
   are as trustworthy as DPP requires; custodian endorsements are
   checked for validity periods and revocation; and verifiers never
   accept a key carried with the evidence itself.  A compromised
   custodian key can sign false receipts until its endorsement expires
   or is revoked.  Evidence can be stripped by any forwarder; stripping
   shows as a gap.  Receipts and hop-records reveal routes and timing to
   anyone who can read the bundle.
